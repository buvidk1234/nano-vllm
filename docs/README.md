教程以本仓库包含 chunked prefill 的 Nano-vLLM 实现为对象，所有调用关系和状态变化都对应文中链接的源码。

## 案例定义与章节衔接

系统主例使用可控制长度的 token ID：

```python
prompt_a = [42] * 512 + [43] * 88  # 600 个输入 token
prompt_b = [42] * 512 + [44] * 88  # 600 个输入 token，与 A 的前 512 个相同
prompt_c = [21, 22, 23]           # 3 个输入 token
```

token ID 是词元在模型词表中的编号。Python 表达式 `[42] * 512` 将编号 42 重复 512 次，`+` 拼接两个列表，因此 A 的输入长度为 `512+88=600`。这些编号用于构造固定长度和共享前缀，不代表特定的自然语言句子。

输出数量由每条请求的 `SamplingParams.max_tokens` 指定：A 为 3，B、C 各为 2，与输入列表的构造是两个独立设置。A 的输出记为 Y1、Y2、Y3，B 为 Z1、Z2，C 为 W1、W2；字母代表实际采样出的 ID，不预设生成文本。

- 01 只提交 A，Prefill 预算为 1024，一轮处理完整输入。
- 03 从新的空闲引擎开始，把预算改为 256；A 完成 Prefill 后才加入 B，B 完成后加入 C。
- 04 明确改变 C 的入队时机，让 A、B、C 能参与同一轮 Decode。
- 02 将单次模型计算缩小到两词、四维向量，以便手算。它不是 600-token 请求的真实数值输出。04 的分片算术继续使用这套小权重。

章节中的变体分别声明初始条件。例如，04 从 C 提前入队的时间线继续，A、B、C 此时都仍持有各自的块引用。

## 阅读约定

位置、张量行号、块号从 0 开始，输出 Y1 表示第一个生成 token。块大小使用源码默认值 **256**。`num_tokens` 是已知 token 总数，`num_cached_tokens` 是 CPU 记录的 KV 进度，`num_scheduled_tokens` 是本轮输入量；每张状态表都会说明记录时点。

形状中的 T 是本轮输入行数，N 是请求数，H 是隐藏维度，d 是头维度。PyTorch Linear 权重为 `[out,in]`，计算为 `XWᵀ`。`enforce_eager=True` 只关闭执行器的 CUDA Graph，局部 `torch.compile` 仍然存在。

请求长度、模型尺寸和容量数字均为文中明确设定的教学条件。代码片段用于说明接口和计算，状态表与数值结果已在正文展开。
